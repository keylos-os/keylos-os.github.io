EXPERIMENTAL / LINUX-BASED OS

A Linux workstation
for coding agents.

An agent needs to edit files, run unfamiliar code and talk to services. Keylos is being built to give it that access with specific limits on each program.

The OS manages file grants, credentials, external actions and recovery. You choose the project it can change, the destinations it can reach, and the effects that need your approval.

02 / THE SYSTEM UNDERNEATH

Where the checks live.

Keylos organizes Linux userspace around small services. These are the boundaries the full system is designed to enforce.

A

Authority & isolation

broker / warden / bench

A running program has a principal: program + human + session. Capabilities grant operations on specific resources. Warden confines native processes using namespaces, Landlock, seccomp and cgroups; Bench specifies microVM workbenches for agents and untrusted toolchains.

Process model and isolation tiers ↗
B

Secrets & effects

vault / gate / broker

Vault controls access to secrets. Gate is designed to make authorized external requests, inject destination-bound credentials and enforce budgets. A GitHub token can be used for an approved request without appearing in the agent’s environment.

Secret access and credential injection ↗
C

Code, configuration, data

boot / depot / config / strata

The design separates verified executable code, signed configuration and writable data. Installing code and changing system configuration are explicit operations. Local transactions retain undo points; external effects need their own compensation rules.

Transactions and the limits of undo ↗
D

Progress & evidence

loom / ledger

Loom records workflow state, observations and results. Recovery starts a fresh, re-authorized attempt. Ledger records signed receipts for important decisions and effects, so you can trace a change back to its authority.

Durable execution and recovery ↗
※

Limits and integration costs.

Linux, firmware and the privileged services remain in the trust base. Labels track data exposure; they do not detect prompt injection. Policy uses those labels to restrict subsequent actions. A recorded receipt cannot make an external action reversible.

There is integration work behind each boundary: packaging, effect adapters, trusted approval surfaces, and software that expects a conventional Linux environment. Read the residual risks ↗

SPECIFICATION
Where else could this architecture be useful?+

The same boundaries apply to developer machines with production credentials, sensitive personal computing, audited deployments, fleets and kiosks, Kubernetes nodes, and legacy software. The handbook covers these as system profiles. The shared protocols also make the project useful for security research and conformance work. The coding-agent workstation is the first integration target.
