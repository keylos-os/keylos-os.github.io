# Harness API

> A harness is the agent loop: it calls the model, interprets its output, runs tools, and repeats. In keylos a harness runs inside the workbench VM, or as a WASI component inside aide for flow-proof harnesses. It talks to the host only through `AgentHost`.
> This page is for harness authors. It covers the API, provenance reporting, the guest environment and the `keylos-agent-harness` SDK.

**Status:** specified (v1.0). Components: [aide](../../specs/aide/spec.md) (`AgentHost`, `aide-guest`, SDK).

## Where the harness runs

| Placement | Runs in | Can use | Required for |
|---|---|---|---|
| `vm` (default) | The workbench VM, as a normal process started by `aide-guest` | Any language; VM tools directly; host tools via `AgentHost` | Most agents |
| `wasi` | A WASI 0.3 component in `aide-wasi` on the host (Wasmtime, fuel- and memory-limited) | Host tools; MCP; VM tools through the `VmExec` interface | `camel/1` flow proofs |

## Connecting

Inside the VM, `KEYLOS_AGENT_HOST=vsock:2:7002`. Connect with the **capwire-vsock profile** ([protocols §7.2.1](../../specs/protocols/spec.md#721-capwire-vsock-profile-host--guest)): Cap'n Proto RPC over `AF_VSOCK` `SOCK_SEQPACKET`, no fd passing, bulk data through `ByteStream`/`ByteSource`. The bootstrap capability is `AgentHost`, already bound to your session; `AgentHostExt` and `VmExec` come from `Extensible.ext` on the same connection. There is nothing to authenticate: bench forwards port 7002 only for agent VMs, and the host identifies the VM by its CID.

```rust
let host = keylos_agent_harness::connect_from_env().await?;   // AgentHost + AgentHostExt
let boot = host.bootstrap().await?;                           // session id, template, git identity, env
let tools = host.tools().await?;                              // pinned tool definitions (JSON)
```

## The interface

| Method | Use |
|---|---|
| `tools()` | The pinned tool list (template tools plus remote MCP tools as `mcp.<server>.<tool>`) |
| `callTool(name, args, provenance)` | Host tools and remote MCP tools. Returns `(result, label)`. |
| `model(request)` / `modelStream(request)` | Model calls through gate: metered, credentials injected. The request is the provider's native JSON. |
| `emit(event)` | Report messages, tool calls and results, and completion to the human's UI. Structured events beyond the basic variants go in `AgentEvent.rich` (JSON) |
| `requestGrant(reason)` | Ask for new authority |
| `heartbeat()` | Liveness. aide marks a session stalled after 60 s of silence. |

`vm` and `cmd` tools you run yourself inside the VM. Report them with `emit(toolCall)` / `emit(toolResult)` so the human can follow along. These reports are **claims**; observed activity comes from gate and the overlay.

## Provenance: say where every argument came from

When you stage an effect, report the source of each argument:

```json
[
  {"argument": "to",      "source": "user",                                   "label": {"conf": "private", "integ": "user"}},
  {"argument": "subject", "source": "model",                                  "label": {"conf": "private", "integ": "untrusted"}},
  {"argument": "body",    "source": "web:https://example.com/release-notes",  "label": {"conf": "public",  "integ": "untrusted"}}
]
```

| Source values | Meaning |
|---|---|
| `user` | Typed by the human (task text, `keylos.human.ask` replies) |
| `file:<path>` | Read from a share |
| `web:<url>` | Fetched |
| `mcp:<server>/<tool>` | A remote tool result |
| `model` | Generated by the model with no single identifiable source. Labelled with the session label. |

The approval prompt shows this table. aide adds its own **observed** provenance where it can match values to earlier tool results. Honest provenance makes approvals faster: a recipient marked `user` is approved at a glance, a recipient marked `web:` gets scrutiny.

## Handling staged effects

When an effect needs approval:
- `keylos.effect.stage` returns `{state: "staged", approval: "a-…"}`;
- unsafe HTTP requests made through tools return `428 Precondition Required` with `Keylos-Intent: e-…`.

Good harnesses:
1. tell the model the effect is staged, not done;
2. continue with other work, or wait (`keylos.effect.status`);
3. never retry the same request in a loop. That trips the identical-call breaker.

## The guest environment

| Item | Value |
|---|---|
| Network | One virtio-net NIC terminated on the host by `bench-net`; every flow becomes a `ShimEndpoint.connect` on gate. Proxy-aware and non-proxy-aware tools both work |
| DNS | The guest resolver, answered by bench-net from `ShimEndpoint.resolve`: only granted names resolve |
| `SSH_AUTH_SOCK` | gate's signing proxy (`ShimEndpoint.sshAgent`: session git-signing key, granted SSH keys) |
| git | `user.name` = template name + "(agent)"; commit trailers `Assisted-by:` and `Agent-Session:` added by hook; `gpg.format=ssh` with the session key |
| Tokens | None in the guest. bench-net holds the session's network tokens on the host |
| Shares | `/work/project` (overlay), `/work/<name>` (read-only grants), `/agent` (the template's `/.keylos/agent/` directory), `keylos-ca` (session CA, when gate intercepts) |
| Local MCP servers | Started by aide-guest; stdio commands listed in the bootstrap |

There are no credentials anywhere in the guest. Code that "needs an API key" gets it injected by gate on the wire for the hosts the template's injection rules cover.

## The SDK: `keylos-agent-harness`

| Module | Provides |
|---|---|
| `host` | AgentHost client, reconnect with backoff, heartbeat task |
| `tools` | Tool registry from `tools()`; cmdsig → JSON Schema; local MCP stdio client |
| `provenance` | A builder that tracks values from tool results and user input and produces provenance arrays |
| `effects` | Stage helpers; `428` handling for HTTP clients |
| `flowproof` | For `wasi` harnesses: the `camel/1` interpreter runtime and proof builder |
| `events` | Typed `emit` helpers, including the `keylos:` rich-message encoding |

The SDK is optional. Any harness that speaks capwire and the `AgentHost` schema works.

## Building a template

1. Build your harness as an app generation (or a WASI component).
2. Write `template.json`, `tools.json`, `prompt.md` and `policy.json`.
3. Build the template generation with `forge`, which computes the digests.
4. Install it with `depot`; review the capability diff.
5. Run `aide verify <template>` to check pins, including live remote MCP tool lists.

## Limitations

- Harness events are self-reported. Design UIs and reviews around observed data.
- `wasi` harnesses cannot run arbitrary native code on the host by design. Heavy work goes through `VmExec`.
